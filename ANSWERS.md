# Відповіді 

1. **Які системні виклики Linux відповідають головним функціям вашого рішення (назвіть пари «системний виклик ↔ Python API»)?**

Відповідь:

У реалізації задачі 8 використовуються такі основні пари системних викликів та їх аналогів у Python:
* setrlimit(2) ↔ resource.setrlimit() — для встановлення м'яких і жорстких лімітів ресурсів процесу.
* getrlimit(2) ↔ resource.getrlimit() — для отримання поточних обмежень ресурсів.
* fork(2) ↔ os.fork() — для створення дочірнього процесу, у якому застосовуються ліміти.
* wait4(2) / waitpid(2) ↔ os.waitpid() — для очікування завершення дочірнього процесу та перевірки його статусу чи сигналу.
* open(2) / write(2) ↔ os.open() / open().write() — для взаємодії з файловою системою (відкриття /dev/null та запис у тестовий файл).

2. **Які помилки (зависання, подвійне повернення з дитини, незакритий дескриптор, неправильний порядок запису в uid_map, забутий fork після CLONE_NEWPID) ви зустріли або свідомо запобігли, і як саме?**

Відповідь:

Під час виконання завдання було свідомо запобігнено таким потенційним помилкам:
1. Аварійне завершення процесу через сигнали перевищення лімітів (зокрема SIGXFSZ): за замовчуванням ядро Linux надсилає летальний сигнал процесу, що перевищує ліміт RLIMIT_FSIZE. Для запобігання падінню у функції file_size_limit явно ігнорується цей сигнал через signal.signal(signal.SIGXFSZ, signal.SIG_IGN), що дозволяє коректно перехопити помилку ОС EFBIG та повернути кількість записаних байтів.
2. Проблеми з життєциклом дочірнього процесу: після завершення виконання цільової функції job() дитина викликає os._exit() замість стандартного sys.exit(), що запобігає подвійному скиданню буферів виводу батьківського та дочірнього процесів.
3. Неперехоплені винятки: будь-яке виключення всередині виконання job() обгортається у блок try...except і завершується кодом 3, захищаючи батьківський процес від зависань.


3. **Чого ваша частина міні-контейнера не ізолює або не обмежує (спільне ядро, мережа, права, seccomp) і чому «контейнер» без цього не можна вважати безпечною пісочницею?**

Відповідь:

Реалізований за допомогою rlimit механізм відповідає лише за кількісне обмеження ресурсів (дескриптори, пам'ять, час, розмір файлів) для процесу. Проте він принципово не забезпечує повної ізоляції, оскільки:
* Не створює нових просторів імен (namespaces), тому процес залишається у глобальній мережі, спільному дереві процесів і спільному просторі хоста.
* Не ізолює файлову систему (відсутній chroot або mount namespace), дозволяючи доступ до загальних системних ресурсів.
* Не фільтрує системні виклики (відсутній seccomp) і не обмежує привілеї ядра.

Без цих компонентів процес повністю залежить від спільного ядра Linux і не захищений від мережевих атак чи маніпуляцій з іншими процесами, тому такий ізольований лише за лімітами процес не можна вважати повноцінною безпечною пісочницею.
